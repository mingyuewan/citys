# 渲染说明：Blender 场景与网页实时渲染优化

本文记录 2026-10-22 这一轮的工作：用 Blender 搭建可编辑场景并离线渲染，同时修正网页 WebGL2 渲染器中已有证据的问题。文中的数字都来自这台机器上的实际运行（Intel i7-9750H 6 核 12 线程，AMD Radeon Pro 5300M，macOS，Chrome 无头模式 + ANGLE Metal）。

## 1. 素材

三张纹理由**内置 GPT Image 工具**生成。提示词原文保存在 `assets/image-prompts.json`，路径清单见 `assets/manifest.json`。

| - | - | - | - |

网页使用的是 `tools/make_web_textures.py` 缩到 512 px 的版本（`assets/web/`，三张共约 146 KB），由 `tools/assemble3.py` 以 data URI 形式嵌入 `index.html`，页面仍是单文件，可离线打开。如果页面没有经过组装，会自动退回到原来的程序纹理。

## 2. Blender 场景

- **版本**：Blender 4.5.14 LTS（Intel x86_64 官方构建），从挂载卷直接运行，没有安装到 /Applications。
- **文件**：`blender/shenzhen-bay.blend`（zstd 压缩，约 14 MB，5 张纹理已打包）。
- **几何来源**：`tools/blender/export_scene.py` 在无头 Chrome 中打开页面，等 `buildScene()` 完成后，用 `gl.getBufferSubData` 读回网页实际使用的 GPU 缓冲（每个顶点 13 个 float，共 52 字节，索引为 Uint32）。所有几何都没有重新建模：
  - 11 座地标各自是独立对象（`LM_xx_…`，自定义属性中有中文名、高度和数据来源说明）；生成楼体合并为 `Generated_Buildings` 一个对象；另有桥梁、球场/泳池/停车场。
  - `Island_Body_and_Islets`：岛体、垂岩、藤蔓和 10 座小浮岛；`Waterfalls`：网页的瀑布面片，`fall_u/t/edge` 存为属性。
  - `Ground_and_Bay`：按网页 `isleR()` 轮廓生成的圆盘，材质读取网页导出的地面分类图（r 通道为水，g 为绿地，b 为道路）和用地图。
  - `Roads_and_Sidewalks`：网页的道路条带，横向坐标、纵向坐标、路口距离、半宽、车道数、单行标记、类型都存为属性，车道线和斑马线由着色器绘制。
  - 实例：行道树、灌木、棕榈、小浮岛树（约 2.8 万）、路灯、停车、车流快照、红绿灯、公交站（约 2 万）、云卡片（约 1500）都是点云加几何节点 Instance on Points。整个场景共 39 个对象（其中 7 个是隐藏的模板）。
  - 网页关闭了背面剔除，并在着色器里翻转背面法线，所以原始三角形大多是顺时针绕序。导入时按网页法线逐个三角形重新确定绕序，并把网页法线写成自定义法线。
- **坐标**：Blender (X, Y, Z) = 网页 (x, −z, y)，单位米，原点 22.5150°N 113.9420°E。
- **材质**：共 28 个，按网页材质编号映射。屋顶面（法线朝上或顶盖 UV）统一使用混凝土材质。写字楼、住宅、裙楼、城中村分别用幕墙纹理或程序窗格；地面和水面混合使用；道路线、瀑布、云海、车漆（每个实例的颜色来自网页车流数组）都有对应材质。
- **灯光与色彩**：太阳方向沿用网页 `sky()` 的太阳模型，取 16.9 时（低角度暖光，从西南偏西照来），强度 5，角直径 0.8°；天空使用 Nishita（海拔 1500 m，空气密度 1.3，尘埃 0.35，臭氧 1.6，强度 0.22）。色彩管理为 AgX，Look 为 Medium High Contrast，曝光 +0.15。
- **合成**：开启 Mist 和 Environment 通道，胶片设为透明。远景雾按 Mist 混合（起点 3 km，深度 70 km，二次衰减），再把天空叠在背后，最后加 Fog Glow 辉光和 1.12 倍饱和度。云海平面边长 800 km，边缘落在地平线雾中，不会露出硬边。
- **渲染设置（成品实际使用）**：Cycles CPU，128 采样，自适应阈值 0.02，OpenImageDenoise 降噪；最大反弹 4 次（漫射 2，光泽 2，透射 2，透明 24），间接光钳制 6，关闭焦散。文件中默认保存的采样是 96，渲染命令传入了 128。

## 3. 网页实时渲染的修改（`src/city.src.html`）

1. **HDR MSAA 能力与 FBO 完整性**：采样数改用 `getInternalformatParameter(RENDERBUFFER, fmt, SAMPLES)` 按格式查询，不再用全局的 `MAX_SAMPLES`。每个 FBO 都调用 `checkFramebufferStatus` 检查，失败时依次回退：RGBA16F MSAA → RGBA8 MSAA → RGBA16F 无 MSAA → RGBA8 无 MSAA。无 MSAA 时直接画进场景纹理，并跳过 blit。bloom 阈值改为按实际格式（`RT.hdr`）选择。
2. **阴影尺寸与 PCF**：删除写死的 `SM.size = 3072`。尺寸改为 `min(MAX_TEXTURE_SIZE, MAX_RENDERBUFFER_SIZE, 目标值)`：桌面 3072，粗指针或小屏幕设备 2048。阴影贴图改用 `texStorage2D`，并检查 FBO；失败时降到 2048、1024，再失败就关闭阴影，不会黑屏。`shadowAt` 从 3×3 共 9 次比较采样改为 4 次（偏移 ±0.6 texel，叠加硬件 2×2 比较过滤）。动态分辨率降到最低档时，阴影贴图一次性降为 2048。
3. **动态分辨率**：缩放比例改为固定档位 `[1, 0.85, 0.72, 0.6]`，每次只变一档。降档需要连续约 2 s 的慢帧，且距上次调整超过 4 s；升档需要约 6 s 的快帧，且间隔超过 10 s；页面隐藏时不调整。
4. **布局读取**：CSS 尺寸由 `ResizeObserver` 缓存（不支持时退回 resize 事件），渲染循环和标签布局不再每帧读取 `clientWidth`/`clientHeight`。
5. **拾取**：改为永久的 1×1 FBO，并收窄投影矩阵，让被点击的像素填满这个 1×1 视口。画布或分辨率变化时不再重建全分辨率拾取缓冲，回读也只有 1 个像素。
6. **WebGL 上下文丢失**：`webglcontextlost` 时调用 `preventDefault`，停止绘制并提示用户；`webglcontextrestored` 时重新载入页面（数据都嵌在页面里，离线也能重建）。
7. **纹理接入**：见第 1 节。

没有改动 UI 和交互，也没有新增运行时网络请求。页面原本就会请求 Google Fonts，这次保持不变；离线时会回退到系统字体。

## 4. 验证（`tools/webgl_check.py`，无头 Chrome，GPU：ANGLE Metal / AMD Radeon Pro 5300M）

基线是首版提交中的 `index.html`（`git show HEAD:index.html > build/baseline.html`）。两版使用同一套伪时钟、视角和分辨率，每帧执行 tick 后用 1 像素 `readPixels` 等待 GPU 完成。

- **启动与功能（新版）**：4–6 s 内完成构建；除一条 404 外没有控制台错误（这条 404 推测是 favicon，基线同样存在）；`gl.getError() == 0`。渲染目标为 RGBA16F MSAA×4（本机 RGBA16F 支持 8/4/2 倍采样），阴影 3072，三张纹理都已加载。
- **日夜与视角**：总览、城市（日）、城市（夜）、街道四个视角的截图都正常，没有黑屏。截图平均亮度分别为 163、128、21、129。
- **拾取**：点击最高地标正确打开“华润大厦（春笋）”信息卡。
- **窗口尺寸**：800×600、390×844、1600×900、1280×720 四种尺寸下，画布和渲染目标尺寸都正确跟随，没有 GL 错误，画面不黑。
- **回退路径**（`--fallbacks`，通过 init script 模拟能力缺失）：RGBA16F 不支持多重采样时变为 “RGBA8 MSAA×4”；完全不支持 MSAA 时变为 “RGBA16F 无 MSAA”。两种情况都能正常出图，没有 GL 错误。用 `WEBGL_lose_context` 模拟上下文丢失：丢失时显示“显卡上下文已丢失”提示，恢复后页面重新载入并完成重建。
- **帧时间 A/B**（中位数，ms/帧，基线 → 新版）：

  | 视角 | 1280×720 第 1 轮 | 第 2 轮 | 第 3 轮 | 2385×1341（2560×1440 窗口，受 320 万像素上限约束）第 1 轮 | 第 2 轮 |
  | - | - | - | - | - | - |
  | 总览（日） | 23 → 23 | 23 → 23 | 24 → 19 | 30 → 30 | 30 → 30 |
  | 城市（日） | 25 → 24 | 25 → 25 | 24 → 20 | 33 → 31.5 | 34 → 33 |
  | 城市（夜） | 26 → 26 | 26 → 26 | 26 → 26 | 34 → 35 | 35 → 35 |
  | 街道（日） | 25 → 23 | 24 → 24 | 25 → 24 | 29 → 29.5 | 33 → 32 |

  **结论**：在这台机器上，两版的差异基本落在各轮之间的波动范围内（第 3 轮的 19/20 ms 没有复现）。因此**不声称帧率提升**。可以确认的是，新版增加三张纹理后没有变慢。推测本机帧时间可能受 CPU/JS 侧限制（车流、空中物体、云排序、标签），尚未通过 profiler 验证；阴影 PCF 减少的 fetch 在高分辨率下也没有测出差异。在填充率受限的移动 GPU 上可能有差别，但这里没有设备可测。
- **动态分辨率重分配**（`--dynres`，真实 rAF 加合成 CPU 负载，统计 40 s 内渲染目标的重分配次数）：
  - 负载与像素数成正比（全分辨率约 45 ms/帧）：基线 2 次（1088×612 → 925×520），新版 2 次（1088×612 → 922×518），两者都稳定在约 0.72 倍。
  - 间歇卡顿（每 8 s 中有 2.5 s 为 55 ms/帧，其余 4 ms）：**基线 18 次**，尺寸在 1088×612、1175×661、1269×714、1280×720 之间反复变化；**新版 0 次**。

## 5. 尚存限制

- 阴影仍然每帧整体重画（车辆等动态物体也投影），没有做静态阴影缓存。这需要拆出第二张阴影贴图，本轮没有做。
- 动态分辨率降档时仍会整体重建渲染目标（只是次数少了很多）。“按容量分配，用子视口渲染”的方案需要改动所有全屏 pass 的 UV，本轮没有做。
- 拾取仍然是同步的 `readPixels`，但只在点击时执行，且只读 1 个像素。
- Blender 场景是静态快照：车流取导出时刻，没有动画；夜景灯光只为幕墙纹理的暖窗接了自发光（强度为 0），没有渲染夜景成品。`render.py --engine EEVEE` 可以运行，但没有用它出成品，也没有验证效果。
- 网页中的生成楼体、球场、停车场、车辆、行人都是程序生成的，海岸线和绿地由路网推算。Blender 场景完全继承这一点，对象的自定义属性和场景的 `source_note` 中写有说明。道路 © OpenStreetMap 贡献者（ODbL），地标坐标与高度来自维基百科。
- 没有导出 glb（brief 中为可选项）。
