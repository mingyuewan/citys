# 调研：shibuya-rain-walk 的渲染做法、我们的优化空间、codex + Blender 建模管线（2026-10-22）

问题有三个：

1. shibuya 的画面主要靠什么做出来的？three.js 在里面起什么作用？
2. 对照它，我们的 three.js 迁移还有哪些优化空间？
3. 用本地 codex CLI 调 GPT Image 生成图片、用 Blender 建模，这条管线能不能走通，应该怎么用？

文中的数字都来自这台机器（i7-9750H，Radeon Pro 5300M，Chrome 无头模式 + ANGLE Metal，1280×720）。

## 1. shibuya-rain-walk 实际是怎么做的

源码版本：`Zenojz/shibuya-rain-walk` @ `1330e2a`（2026-10-22），`night/src` 下约 1.17 万行 JS。

### 1.1 画面主要来自手写着色器

| 用法 | 次数 | 说明 |
| - | - | - |
| `ShaderMaterial(` | 61 | 楼体立面、地面、天空、雨、光晕、招牌、人群、远景城市，各有各的着色器 |
| `onBeforeCompile` | 3 | 只在少数地方改 three.js 自带材质，例如 Ink 描边的法线/深度记录 |
| `MeshStandardMaterial` / `MeshBasicMaterial` | 8 / 14 | 主要用于人物、小物件、调试 |
| `mergeGeometries` | 34 | 静态物体按材质合并成少数几个网格 |
| `InstancedMesh` / `InstancedBufferAttribute` | 11 / 14 | 光晕、行人、车、雨等 |
| `frustumCulled = false` | 50 | 合并后的大网格和着色器里做位移的物体，都关掉了视锥剔除 |
| `.layers` | 33 | 用图层挑选哪些物体参与阴影、反射、描边 |

共享 uniform 的做法和我们一样：`materials.js` 里有一个全局 `U` 对象和一段 `GLSL_COMMON`（雾、天光、街道光照贴图、阴影查询、噪声），所有材质引用同一份。

### 1.2 three.js 提供的是底层设施

- **加载**：`GLTFLoader` 加 three-vrm 加载人物（`.vrm`），动作来自 `ual-standard.glb`。
- **骨骼动画**：人物和人群。
- **实例化**：`InstancedMesh` / `InstancedBufferGeometry`。
- **后期**：`EffectComposer` → `RenderPass` → 保存一张半分辨率的“玻璃后面”画面 → NaN/Inf 保护 → `UnrealBloomPass` → 调色 → Ink 描边 → `OutputPass`。
- **阴影**：`DepthTexture` 加正交相机，加自写采样（4 次或 9 次）。没有用 three.js 自带的 `shadowMap`（`castShadow` 只出现 6 次）。

### 1.3 值得注意的具体技术

- **只在需要的地方画阴影**：`SunShadow` 只在屋顶、白天、玩家周围 64 m 内画；`LampShadow` 只在夜间街道、玩家周围 44 m 内画，方向取最近几盏路灯的加权平均。阴影投射物用图层（`SHADOW_LAYER`）挑选。
- **烘焙光照（`LightPainter`）**：店面光池、路灯光圈、楼脚接触阴影，在启动时一次性从上往下画进一张半精度纹理（2048²）。每个表面按自己的 xz 坐标和高度采样它，夜间街道的光几乎不需要实时计算。
- **镜面反射**：湿地面的反射是半分辨率的平面镜（`Mirror`），只在地面是湿的时候渲染。
- **Ink 描边**：用 `MeshNormalMaterial` 加 `onBeforeCompile` 把整个场景再画一遍，记录法线和距离，再在后期里按距离跳变和法线转折画线。代价是多一次全场景绘制。
- **远景城市（`FarCity`）**：7 km 半径内 30 m 以上的楼按真实轮廓建，低矮街区按街道走向生成，夜里每扇亮窗是一个点。数据单独烘焙成 `farcity.json`。
- **时段预设（`PRESETS`）**：落日、晴夜、雨夜三套参数，包含太阳、环境光、雾、湿度、亮灯率、曝光、bloom 参数。这和我们阶段 4 的“三个精调的时段预设”是同一个思路。
- **动态分辨率**：每 2 秒统计一次平均帧时间，超过 24 ms 降 0.125 倍像素比，低于 14 ms 升 0.125 倍，范围 0.85 到初始值。
- **NaN 保护**：bloom 之前用浮点位判断把 NaN 和 Inf 换成黑色，避免 Safari 上出现整块黑或白。
- **调研文档**：`night/docs/research/` 里每个大功能都有一篇，先查资料（实拍、规范、照明设计报告）再动手。

### 1.4 它没有用 Blender 建楼

楼体全部来自 OSM 轮廓加一个立面着色器（`city.js`：玻璃幕墙、写字楼逐层亮灯、住宅窗户、底层店面）。外部模型只有人物（VRM，每个 11–16 MB）和动作。首次加载约 200 MB，主要就是这些人物。

**结论**：shibuya 好看，主要靠统一画风的手写着色器、真实的 OSM 数据和大量烘焙，不是靠精模。它的尺度是步行的 440 m 见方，我们的是 6 km 的鸟瞰，屏幕空间的效果（镜面、描边）对我们的收益会小很多。

## 2. 我们的现状与实测

### 2.1 帧时间（中位数，1280×720，每帧含 1 像素回读等待 GPU）

| 页面 | 总览 | 城市俯瞰 | 街道 | 城市夜景 |
| - | - | - | - | - |
| 旧版 `index.html`（全部图层） | 22.0 ms | 23.0 ms | 22.0 ms | 24.0 ms |
| 新版 `web/`（目前只有岛体、城市、地面、天空、云海、阴影、bloom） | 8.0 ms | 7.0 ms | 7.0 ms | 13.0 ms |

新版的数字不能直接和旧版比，因为路面、树、车、行人、飞行器、瀑布、云团、标签都还没有迁移。

### 2.2 旧版的时间花在哪里

用同一套伪时钟逐项关闭后测量：

| 项目 | 耗时 | 依据 |
| - | - | - |
| CPU（JS） | 约 5 ms | 不回读、只跑一帧 JS 的时间 |
| GPU 合计 | 约 17 ms | 总时间减 CPU |
| 实例化绘制（树约 2.8 万、路灯、车、行人、红绿灯、公交站） | 5–7 ms | 把 `drawElementsInstanced` 换成空函数 |
| 阴影 pass | 约 3.5 ms（总览） | `SM.on = false` |
| 生成楼体 | 1–3 ms | `S.showGen = false` |
| 云团 | 约 0 | `S.showClouds = false` |
| 点光（车灯、航灯） | 约 0 | 跳过 `POINTS` 绘制 |

新版逐项关闭的测量：改成单面渲染（`FrontSide`）让总览从 9 ms 降到 7 ms。其余几项的差别都在 ±1 ms 的计时误差以内，目前 GPU 并不吃紧。

## 3. 优化空间（按预期收益排序）

1. **实例化物体（旧版 5–7 ms）**：旧版把所有实例都送进 GPU，靠顶点着色器把远处的扔掉，顶点仍然全部处理一遍；阴影 pass 还会把树、路灯、车再画一遍。迁移时改成：
   - 按网格分块的 `InstancedMesh`，每块有包围球，交给 three.js 做视锥剔除；
   - 按距离分级：近处完整模型，远处的树用低模或面片；
   - 阴影 pass 只画焦点附近的块。
2. **阴影（旧版约 3.5 ms）**：
   - 城市是静态的。太阳方向和阴影焦点（已按 texel 对齐）都不变时，可以不重画阴影贴图；
   - 阶段 4 改成三个时段预设后，太阳方向只有三个。可以把城市和岛的静态阴影、环境光遮蔽按预设烘焙进贴图，运行时只给车、飞行器这些动态物画一张小范围阴影。这是 shibuya `LightPainter` 思路的扩展，收益最大。
3. **统一三角形绕序、打开背面剔除（实测约 2 ms）**：交接文档已经推荐。需要在 `world.js` 的 `frustum`、`gableRoof`、`shell`、岛体 `rockBody` 里统一成逆时针，并去掉着色器里的背面法线翻转。
4. **每帧常量移到 CPU**：`skyAmb()` 在每个像素里调用一次 `skyColor()`，但结果每帧只取决于时间。改成 uniform，城市、地面、路面、树、实例物体的着色器都能省掉这部分。
5. **按材质拆分着色器（待测）**：现在一个 `meshFS` 用 `vMat` 分 20 个分支，玻璃的内透映射（interior mapping）和体育场标线都在同一个程序里。按 shibuya 的做法拆成玻璃、住宅/城中村、岩体、场地标线几个程序，可以减少寄存器压力。同一个三角形内分支是一致的，收益需要实测确认。
6. **夜间光照烘焙**：地面着色器每个像素计算道路夜光。可以像 `LightPainter` 一样，启动时把路灯光池、道路夜光、楼脚接触阴影画进一张俯视贴图。路面迁移过来后，旧版“路面盖住地面道路光”的问题也就不存在了。
7. **后期**：
   - 保留现有 bloom 链（亮部提取、4 级降采样、4 级升采样、合成），比 `UnrealBloomPass` 少几次全屏 pass；
   - 加上 shibuya 的 NaN/Inf 保护；
   - 只有选了画风 B（描边）才加 Ink。加的话用主 pass 同时输出深度和法线（MRT），不要再画一遍整个场景。
8. **动态分辨率**：旧版已有分档逻辑，迁移时直接搬过来。shibuya 的“2 秒窗口、0.125 步进”可以作为参照。
9. **阶段 2 的 3–5 万栋真实楼**：按区块合并网格，远处换成简化体块。远景可以参考 `FarCity`，单独烘焙一份数据。

## 4. codex + Blender 建模管线

### 4.1 本机工具（已确认可用）

- **codex CLI**：`/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`（0.163.0-alpha），不在 PATH 里。`image_generation` 功能开启。
- **Blender**：`~/.cache/codex-tools/blender-volume/Blender.app/Contents/MacOS/Blender`（4.5.14 LTS，Intel 版），之前做离线渲染时用过。

### 4.2 冒烟测试结果

1. **生成图片**：
   ```bash
   codex exec --skip-git-repo-check -s read-only "Use your image generation tool to create exactly one image … <提示词>"
   ```
   - 用时约 1 分钟，消耗 18,811 tokens；
   - 输出 1254² PNG，保存在 `~/.codex/generated_images/<会话 id>/exec-*.png`。
2. **问题：“无缝平铺”不可靠**。测试图是春笋的白色斜交网格加玻璃，2×2 平铺后接缝处的斜杆明显对不上。
3. **Blender 无头建模和导出**：
   - 按网页 `bamboo` 的轮廓建了一个 504 面的锥形塔，节点名 `LM_bamboo`，材质名 `M7_landmark_glass`，贴图导出为 WebP；
   - glb 144 KB，导出用时 0.2 s；
   - 包围盒 x −66.9…−0.9、y 0…392.5、z −247.5…−181.5，与数据中的中心（−33.9, −214.5）和高度 392.5 m 一致，不需要任何坐标换算。
4. **自定义属性没有导出**：中文名、高度、数据来源这些属性需要导出时加 `export_extras=True`。

### 4.3 怎么用

- **GPT Image 适合**：
  - 不规则的自然纹理（岩层、苔藓、沙岩、云片），生成后还要做一步接缝修复（错位一半再融合，或在 Blender 里重新烘焙成可平铺贴图）；
  - 画风 A 的概念样张，先定配色和气氛再写着色器；
  - 小物件的贴图。
- **GPT Image 不适合**：
  - 规则的建筑图案（斜交网格、幕墙格子）：用着色器或 Blender 程序化生成更准，而且天然无缝；
  - 真实地标的参考图：GPT 会编造细节，参考应以实拍照片为准（注意许可）。
- **Blender 的优先级**：
  1. 岛体岩石：在总览、瀑布、岛底三个视角里面积最大，程序生成的岩体最显假，雕刻细节和烘焙环境光遮蔽的收益最大；
  2. 地标：春笋（斜交网格外骨架）、春茧（网壳）、深圳湾一号、腾讯滨海大厦、汉京；
  3. 小物件：树、车、船，导出后在网页里实例化。
- **glb 接入页面的方式（建议）**：
  - 不直接用 glb 自带的 `MeshStandardMaterial` 渲染，否则会和程序生成部分的雾、昼夜、灯光秀、拾取、升起动画脱节；
  - 加载后把网格转成我们的 13 个 float 的顶点格式，用材质名前缀 `M<id>_` 映射到 `mat` 编号，交给同一个 `meshMat`；
  - 贴图通过 uniform 或贴图集传入；
  - 页面按节点名 `LM_<k>` / `ISLAND_body` 替换程序生成的版本，找不到就保持原样（交接文档阶段 3 的约定）。
- **压缩**：
  - Blender 的 glTF 导出只支持 Draco，meshopt 要用 `gltfpack` 做后处理；
  - 网页需要从 `three@0.160.1` 里 vendor `GLTFLoader` 和 `MeshoptDecoder`。

## 5. 建议的顺序

1. 阶段 1 继续迁移剩下的图层（路面、树和实例物体、瀑布、云、空中元素、标签）。实例物体直接按 3.1 的分块和距离分级来做，不照搬旧版。
2. 迁移的同时做两个小优化：统一绕序打开背面剔除；`skyAmb` 改成 uniform。
3. 迁完后用 `tools/compare_views.py` 和帧时间测试做阶段 1 验收。
4. 定画风（推荐 A）。用 GPT Image 出两三张概念样张辅助决定。
5. 阶段 3 先做岛体岩石，再做地标。glb 按 4.3 的方式接入同一套着色器。
